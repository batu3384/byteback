## CA-001 | Critical | Functionality | bridge_scan.cpp:55 ↔ metadata_store.cpp:65 ↔ App.tsx:61 ↔ ResultsView.tsx:127

**Evidence:** Recovery requires `FileRecord.runs` and `startSector` (`recovery_engine.cpp:27-29`: if runs empty → `recoverCarvedFile` → `startSector * sectorSize`). SQLite `files` schema (`metadata_store.cpp:65-83`) stores `start_sector` / `end_sector`, **never writes the data run list**. `GetFilesPage` (`bridge_scan.cpp:55-67`) does not put C++ record's `startSector` / `endSector` / `runs` / `source` / timestamps into the JS object. Live IPC (`bridge_scan.cpp:264-269` + `App.tsx:61-64`) passes only `{name, size}` paths. `ResultsView` (`ResultsView.tsx:127-128`) converts selection id to array index; `recoverFile` receives `startSector=0`, `runs=[]` in most sessions. Engine writes `sizeBytes` from disk start and returns success (`recovery_engine.cpp:247`).

**Why:** Product promise was to extract the file from the correct disk offset. Geometry drops at IPC/DB boundary. User sees "recovered"; content is MBR/GPT/random sector. In forensic context this is silent evidence corruption.

**Direction:** Write run list (and `compressed`) to schema as JSON/BLOB. `GetFilesPage` must return `startSector`, `endSector`, `runs`, `source`, `createdAt`, `modifiedAt`. Make live event a full record or feed recovery only from DB page. ResultsView should use native `id`, not array index.

## CA-002 | Critical | Functionality | ntfs_parser.cpp:174 and :394

**Evidence:** `NTFSParser::scan` reads BPB from LBA 0 (`bootSector[0x0D]` = sectors-per-cluster, line 174-176). On GPT/MBR physical disk LBA 0 is protective MBR, not NTFS boot. Data run translation `run.startSector = previousLcn * sectorsPerCluster` (line 394) — LCN is volume-relative, not disk LBA; `partitionStart` is not added. `NTFSParser` has no `scanAt`; quick scan always calls NTFS at offset 0 (`scan_coordinator.cpp:121-122`). USN pass reads with same `run.startSector * sectorSize` (line 586).

**Why:** For Windows GPT (EFI + Basic Data) and modern MBR (partition usually LBA 2048) MFT FILE magic is found physically, but cluster→sector map is wrong. Recovery (even if CA-001 fixed) reads from wrong LBA. FAT side has `scanAt(partitionOffset)`; NTFS never got the same fix.

**Direction:** Find NTFS boot at partition start (`OEM "NTFS    "` + 0x55AA). SPC and `bytesPerCluster` from there. Physical sector = `partitionStartLba + lcn * spc`. In quick scan use `scanAt` for GPT/MBR "Windows Basic Data" / 0x07.
